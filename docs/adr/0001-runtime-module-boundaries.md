# ADR-0001: Границы runtime-модулей MVP

- **Статус:** принято автором 2026-10-25.
- **Дата:** 2026-10-25.
- **Контекст:** MVP-05 плана задач требует выбрать границы runtime-модулей до начала реализации.

## Контекст решения

Текущий проект UE 5.5 содержит один runtime-модуль `DefendYourKingdom`. Автор утвердил один модуль на MVP, со структурным разделением исходников по `Core`, `Meta` и `Saving`. Это соответствует текущему масштабу проекта и не добавляет сборочные зависимости между игровыми подсистемами.

## Принятое решение

Оставить один runtime-модуль `DefendYourKingdom`. Разделять C++-код каталогами:

```text
Source/DefendYourKingdom/Core    # боевая сессия
Source/DefendYourKingdom/Meta    # цитадель и экономика
Source/DefendYourKingdom/Saving  # данные и локальное сохранение
```

Не создавать отдельные модули `DYKSaving`, `DYKCore` и `DYKMeta` для MVP.

Проект реализуется на C++ без Blueprint-классов и Blueprint-визуализации. Меши, аудио и эффекты связываются из C++ через `ConstructorHelpers::FObjectFinder` или передаются через `UDataAsset`. Баланс хранится в `UDataAsset`/`UDataTable`.

## Контракты и владение UObject

Системы города, кампании и профиля используют узкие C++ API и структуры данных. Общие контракты и данные не зависят от конкретного UI; UI на C++ и карты вызывают публичные игровые API; сохранение сериализует состояние, не владея правилами экономики.

- Использовать нативный `UInterface` для контракта между разнородными объектами, когда вызывающей стороне нужно единообразно проверять возможность действия или вызывать операцию. Не добавлять в интерфейс несвязанные возможности.
- Для взаимодействия клетки и юнита использовать `IDYKInteractableUnit`; клетка проверяет/вызывает контракт, а не конкретный класс бойца.
- Использовать абстрактный `UCLASS` как базу, когда наследникам действительно нужны общая реализация, состояние или жизненный цикл UObject. Интерфейс сам по себе не задаёт владение объектом.
- Хранить долгоживущие ссылки на `UObject` в отражаемых `UPROPERTY` полях с подходящим типом ссылки, обычно `TObjectPtr<T>`. Временные ссылки не переживают сборку мусора; не хранить необработанные сырые указатели как долговременное владение.
- Blueprint events и Blueprint-классы не использовать. Баланс и конфигурация контента остаются в Data Assets/Data Tables.

## Локальное сохранение

Сохранение остаётся частью runtime-модуля в `Saving`. Используется один локальный профиль на базе `USaveGame`; сохраняются данные текущей сессии, включая город, прогрессию, кампанию, миссию/волну и временные отметки. При повреждённом или несовместимом сохранении игра показывает ошибку и не перезаписывает файл автоматически. Времена стройки/улучшений представлены Unix Timestamp (`int64`) и обрабатываются через `UGameInstanceSubsystem`.

## Рассмотренные варианты

1. **Один runtime-модуль с папками `Core`, `Meta`, `Saving` — принято.** Границы логики обозначены каталогами без отдельного графа модульных зависимостей.
2. **Три модуля `DYKSaving`, `DYKCore`, `DYKMeta` — отклонено для MVP.** При необходимости вернуться к ним можно отдельным ADR, если появится подтверждённая независимая граница.
3. **Blueprint-визуализация — отклонена.** Классы игры и UI создаются на C++; используются обычные UE ассеты и C++ Data Assets.

## Последствия

- Не добавлять новые runtime-модули в `.uproject`, Target.cs или Build.cs в MVP-07.
- По мере появления систем проверять, остаются ли API между городом, боем и профилем узкими и направленными.
- Дополнительный модуль можно предложить отдельным ADR при наличии независимой ответственности и понятного направления зависимостей.
- Это решение не утверждает конкретные алгоритмы боя или численные параметры баланса.

## Вертикальный срез

Автор подтвердил один городской экран/карту, одну кампанийную миссию с несколькими волнами, полный набор описанных механик, результат, возврат в город и один локальный профиль. Steam, события и второй город в MVP не входят.
