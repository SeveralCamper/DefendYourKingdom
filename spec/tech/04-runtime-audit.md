# Предварительный аудит UE5.5 и граница Steam

**Технический нормативный раздел.** Вход: [`08-tech-and-production.md`](../08-tech-and-production.md); правила работы: [`AGENTS.md`](../../AGENTS.md).

## P18.07–P18.09 — Локальный QA, Steam и аудит существующего UE5-проекта (решения 14.11.2026)

**P18-Q21: минимально необходимое тестирование, без отдельной громоздкой инфраструктуры.** Автор лично тестирует игровой процесс с приглашёнными тестерами; агент-тестировщик проверяет код и конкретные воспроизводимые сценарии. Использовать встроенные C++ Automation Tests/Spec точечно для чистой логики и критических инвариантов. Где нужен настоящий мир, реализовать несколько узких интеграционных/функциональных проверок по требованиям/существующим сценариям `09-qa.md`, но **не** создавать платформу E2E, тестовую песочницу, массовые mock-системы, отдельный тестовый UI или фиктивное «покрытие ради покрытия». Любой тест должен реально падать при нарушении проверяемого правила; тестировщик обязан описать негативный случай и проверить падение на заведомо неверном поведении либо привести другой убедительный способ подтверждения нефиктивности. Тесты — частью задач, не новый многонедельный проект.

**P18-Q22 / P19-Q36: только локальная машина.** До commit/push — проверенная UE-компиляция, применимые automation tests и независимое ревью. Запуск карты — для runtime-изменений и контрольных срезов, **не для каждой технической микрозадачи**. Packaging — лишь при необходимости предъявить контрольную версию автору, не после каждого коммита. **CI/удалённые runner’ы не внедрять**; локальные проверки не заменяют тестирования на иных платформах.

**P18-Q23: обязательная субагентная модель.** Оркестратор назначает отдельного исполнителя, тестировщика и независимого ревьюера; тестировщик и ревьюер сообщают фактические проблемы. Недоступность агентных инструментов — честный блокер, а не фиктивное подтверждение.

**P18-Q24 с уточнением P19-Q36: сборка и проверка по сути задачи.** UE-компиляция проверяется перед commit/push, запуск соответствующей игровой сессии требуется при изменении runtime-сценария; **для чисто архитектурной, документационной, структурной задачи демонстрационный запуск не обязателен**. Полный сквозной запуск и возможность автору посмотреть игру — на `M1-SLICE`/`M2-FULL`; отдельный packaged-билд делать по необходимости. Применимые содержательные тесты/негативные случаи обязательны, но без тестов «для галочки».

**P18-Q25: Steamworks включить в обязательный общий план**, но изолировать через адаптер/сервис, чтобы локальный игровой цикл можно было создать и запустить без Steam API. После подтверждения доступов внедрять необходимые интеграции по зависимостям; не путать `Steam Cloud` с защищённой онлайн-персистентностью. Конкретные Steam AppID, пакеты, ключи, доступы и возможности проекта проверять по окружению, не придумывать.

**P18-Q26: отложенная серверная реализация.** Целевая архитектура — авторитетный бэкенд + БД + Steam login + проверяемые транзакции/время/позже рейтинги. **НЕ реализовывать бэкенд до демонстрации полного работоспособного локального игрового цикла**, несмотря на то, что контракты и границы должны быть отражены в PRD до начала разработки. Бэкенд включён в полный план развития, но не в первую реализацию разработческой сборки.

**P18.09 STATUS: CONTRACT APPROVED / RUNTIME AUDIT PENDING (`AUDIT-00`).** В этой сессии нет фактического `.uproject`, исходников `Source/`, `Config/`, карты `Content/` и конфигурации установленного UE5.5 MCP. Поэтому перечень имеющихся классов, успешная компиляция, схема Blueprints, текущие плагины, качество кода и работоспособность карты **не подтверждены**. Не переводить P18 в `COMPLETED` только после документационного анализа. Для проверки потребуются актуальные файлы проекта/доступ к репозиторию и локальная среда UE5.5: (1) инвентаризация и сравнение с PRD; (2) реальная сборка и запуск; (3) доступные UE5.5 MCP-инструменты и операции над Blueprint; (4) аудит существующих ассетов и лицензий; (5) список сохранить/адаптировать/удалить с аргументами; (6) риски и результаты независимой проверки. Если `Content/` велик, на первом проходе достаточно репозитория/`uproject`/`Source`/`Config` + перечня ассетов; полноценную проверку загрузки карт нельзя засчитать без нужных `.uasset`/`.umap` и UE окружения. **Согласно прямому решению автора, этот аудит выполняет Codex как ПЕРВУЮ обязательную подготовительную операцию, когда получит реальный проект; никаких повторных вопросов о наличии исходников здесь не задавать. P19 можно документально проработать и предварительно утвердить без притворства, что исходники уже проверены. После явного авторского допуска агента к подготовительному аудиту сначала выполнить `AUDIT-00` без изменений геймплейного кода; при обнаружении противоречия с PRD — остановиться, представить отчёт и согласовать корректировку плана **до первой задачи реализации**. Нельзя объявлять P18.09 фактически завершённым до такого отчёта.**

**P18-Q27 / P19-Q33: аудит существующего проекта, прежде чем писать новую систему.** Не предполагать, что проект пуст: найти фактические C++-классы, уровни, сохранения, Blueprint-ассеты, подключённые UE5 MCP, Steam dependencies, возможности локальной сборки; сохранить рабочие части, несовместимое рефакторить точечно. **Исходный `.uproject`/репозиторий не предоставлен при составлении этой редакции; фактический аудит НЕ ПРОВЕДЁН.** Отсутствие репозитория не разрешает объявлять P18.09 завершённым.

**P18-Q28: качество кода и производительность — с первого этапа.** SOLID/DRY/KISS/YAGNI применяются по существу: понятные владельцы состояния, минимум абстракций, правильные структуры данных/алгоритмы, отсутствие ненужных `Tick`/IO, безопасный жизненный цикл UE-ссылок и событий. Не допускать измеримых регрессий по времени кадра/памяти; измерять Unreal Insights/Memory Insights на фактическом тестовом ПК. Не выдумывать аппаратный норматив, пока он не установлен автором.

## P19-Q34/Q35 — детерминированный план исполнения (документально подготовлен, НЕ команда реализовывать)

Нормативный черновик будущего исполнительного порядка — [`12-execution-backlog.md`](../12-execution-backlog.md): фиксированные ID задач, конкретные результаты, зависимости и критические проверочные сценарии. **Перед началом первой кодовой задачи `AUDIT-00`: все документы PRD прочитаны полностью, реальный `.uproject` и код проанализированы, текущая сборка проверена, UE5.5 MCP/Blueprint оценены, риски доложены.** Затем `M1` — рабочий минимальный сквозной игровой цикл; `M2` — весь играбельный локальный MVP со всеми системами, на временных данных и лицензированном визуале (без аудио). Все задачи малы и функционально завершены; стандартный локальный QA-гейт P18-Q12 обязателен перед commit/push. До `POLYGON_ACCEPTED` только черновая тестовая карта, даже если она основана на будущей первой сюжетной. После приёмки разрешается делать финальную сюжетную карту. **Сервер/онлайн/античит/реплеи/Steam-онлайн функции не входят в M1/M2.**
