# AGENTS.md — DefendYourKingdom

## Роль и ограничения

- Проект — самостоятельная стратегия/Castle Defense на **UE5.5**. Игровые системы — **C++** (один runtime-модуль); **Blueprint разрешён только там, где рациональнее для UI/анимации/визуала**, без выноса игровых правил в отдельные Blueprint-реализации.
- **Не начинать AUDIT-00 или программирование без прямой команды автора.** PRD подготовлен, но документы не являются разрешением действовать.
- Первая версия — полноценный **локальный** DEV-MVP, с качественными бесплатными лицензированными временными 3D/2D-ассетами и рабочим UI; **без аудио, серверов, рейтингов, реплеев и античита**. Не создавать dev-панель/редактор баланса.
- **Сначала `AUDIT-00`**, затем задачи `M1` → `M2` по зависимостям в [`spec/12-execution-backlog.md`](spec/12-execution-backlog.md). Финальные сюжетные/бесконечные карты **запрещены до явного `POLYGON_ACCEPTED`** после полной авторской проверки полигона.

## Правило минимального контекста — обязательно для всех агентов

1. **Маршрут — [`README.md`](README.md).** Прочитать его и `spec/00-project-and-roadmap.md` один раз для общего контекста. Не читать `spec/` рекурсивно в каждую задачу.
2. **Одна задача → одна подборка.** Прочитать только строку ID и зависимости из `spec/12`, затем соответствующую строку `spec/13`; открыть лишь перечисленные *предметные* разделы. В этих файлах использовать поиск по ID/заголовку и читать локальный участок, а не соседние темы без необходимости.
3. **Паспорта:** `spec/10` и `spec/11` — индексы. Для работы с конкретным союзником/врагом читать только **его файл** в `spec/catalog/allies/` или `spec/catalog/enemies/`. Поля `НУЖНО ЗАПОЛНИТЬ` не стирать и не додумывать как окончательный контент.
4. **Техника:** `spec/08` — индекс, читать один нужный документ из `spec/tech/`. Не загружать отложенные онлайн-требования в задачи локального боя, если не меняется общий контракт.
5. **QA:** брать test-ID из `spec/13`, путь — из `spec/qa/test-index.tsv`, читать только нужные тесты и их общие инварианты. Вся матрица полигона читается при `M2.21` / финальной приёмке.
6. **Субагенты:** исполнитель получает требования + затронутые паспорта; независимый тестировщик — критерии/негативные QA; независимый ревьюер — diff, инварианты, результаты. Не копировать полные тексты PRD/QA каждому. Передавать ссылки/ID и узкие выдержки. При изменении PRD перечитать **соответствующие** файлы.
7. **Исключение `AUDIT-00`:** первичная проверка всего комплекта и фактических UE `.uproject`/`Source`/`Content`/`Config`/плагинов/MCP и сборки; проходить документацию тематическими частями, результат — краткая карта существующих компонентов. **Не выдумывать** код, ассеты, тесты и окружение.

## Источник истины и временные параметры

- **Механики** — `spec/01…07`, **авторские численные поля** — индивидуальные `spec/catalog/` паспорта; **технические требования** — `spec/tech/`; **QA** — `spec/qa/`. Индексы не заменяют предметную норму.
- Физическая/магическая броня — **плоское целочисленное вычитание**; HP гоблина-убийцы **15**, обычного гоблина **10**; ресурс в городе — **еда**; длительные эффекты обнуляются на границе волны; в `CHALLENGE_5` HP **всех** защищаемых объектов = 1.
- Для незаполненных параметров внутренней сборки допускается только заменяемая конфигурация `DEV_PLACEHOLDER` без подмены утверждённых чисел и механик. Подробности — [`spec/OPEN_FIELDS.md`](spec/OPEN_FIELDS.md), [`DEV-MVP-EXEC`](spec/tech/05-dev-mvp-policy.md).
- Не добавлять новые механики, фракции, классы героев, реальную монетизацию, отдельные runtime-модули или финальные способности боссов без решения автора. Не заводить неуместные исторические справки, переписки и длинные журналы в нормативных документах.
- Код — SOLID, DRY, KISS, YAGNI, без ненужных `Tick`/зависимостей. Существующий работающий код сначала сохранить/адаптировать по результатам аудита, а не переписывать всё заново.

## Качество, Git и отчётность

- **Алгоритм каждой задачи:** прочитать узкий набор требований → реализовать → реально собрать затронутый проект и прогнать применимые автоматические функциональные/негативные тесты → исправить найденные дефекты → обновить журналы и сделать коммит → кратко сообщить результаты и попросить автора проверить изменения. Отдельные независимые агенты тестирования/ревью не являются обязательным этапом; итоговое игровое и визуальное ревью выполняет автор. Если сборка/автотесты недоступны — `BLOCKED`, а не фиктивный `PASS`. Незатронутый проверенный коммит при повторном `push` не требует второй идентичной сборки.
- **Без самостоятельных игровых прогонов, скриншотов, визуальной проверки, cook/package и демонстраций.** Выполнять их только по отдельной прямой просьбе автора. Безрендерный запуск UE для автоматических тестов разрешён. После тестов просить автора проревьюить результат; личная приёмка `M2-FULL` и явный `POLYGON_ACCEPTED` остаются обязательными перед финальными картами.
- Работать в текущей ветке, если автор не просил иного. **После каждой выполненной задачи обязательно обновлять [`Changelog.md`](Changelog.md) в существующем формате, делать коммит `Task-xxx: <что сделано>`** Номер коммита продолжает существующую последовательность Task, если автор не указал иной. Отдельное повторное разрешение на commit не требуется; явное указание автора не коммитить имеет приоритет. QA-гейт выше обязателен; при блокере не обходить его, сообщить причину незавершённой отправки.
- После задачи кратко отметить «сделано / решения и причины / реально пройденные проверки / ограничения» в [`docs/implementation-log.md`](docs/implementation-log.md) и сообщить автору, включая хеш коммита и результат push.
- PRD актуализируется по авторским изменениям без искусственной заморозки/change-request; технический журнал не имеет права переписывать игровые требования. Спрашивать только о действительно блокирующем продуктовом конфликте.
