# DefendYourKingdom — документация фактической реализации

**Тип документа:** `IMPLEMENTATION_LOG`; **НЕ PRD и НЕ новая игровая спецификация**. Нормативные требования и запланированные задачи находятся в `spec/`; этот журнал отражает только **фактически выполненную** работу Codex в репозитории. AUDIT-00 и задачи M1 выполняются по прямым командам автора; результаты и ограничения приведены ниже.

## Порядок ведения

- **Одна краткая запись на реально завершённую задачу**, включая её стабильный ID (`A00.01`, `M1.03`, `M2.07` и т. п.). Если задача заблокирована, можно явно записать `BLOCKED` и препятствие, но не выдавать за завершённую.
- По существу: **что сделано; какие технические решения приняты; почему выбран этот вариант**; путь к изменённым ключевым модулям/ассетам; **фактически выполненные** сборка/тесты/ревью и их результаты; известные ограничения.
- Без копирования PRD, длинных трактатов, ложных тестов, искусственных скриншотов и пересказа всех строк кода. Ссылки на ID требования/задачи достаточны; по изменению утверждённых игровых правил нужен отдельный процесс согласования PRD, а не запись в этом журнале.
- Перед каждым commit/push действует локальный QA-гейт из `AGENTS.md`; **packaging и показ игрового результата не обязательны для каждой задачи**. Для невизуальной задачи допустима проверка компиляцией и применимыми тестами. Запуск затронутой игровой сцены — когда он действительно проверяет поведение.
- После работы над задачей оркестратор **кратко сообщает автору то же самое**. Развёрнутый отчёт — на `AUDIT-00`, `M1-SLICE`, `M2-FULL` или при материальном блокере.

```markdown
- **Проверено:** [команда/действие → фактический итог; тестировщик; ревьюер]
- **Ограничения:** [если есть, иначе «нет известных»]
- **Git:** [хеш коммита после commit; не придумывать заранее]
```

### M1.03 — локальный профиль и надёжное сохранение — 15.11.2026 — DONE

- **Сделано:** сохранена существующая модель `DYKProfileSaveGame`; `DYKSaveSubsystem` записывает две чередующиеся копии с версией контейнера/схемы, монотонной ревизией и SHA-1 метаданных и данных. Добавлены `IDYKProfileService`, снимок только для чтения и команды с сохраняемым ID. Повтор подтверждённого ID не исполняет callback; отклонённая команда или ошибка записи не меняет подтверждённый профиль. Офлайн-часы переведены на команды; GameInstance принимает восстановленный профиль.
- **Решения и почему:** синхронная запись на игровом потоке исключает поздние асинхронные перезаписи; один снимок проходит временный файл, проверку чтением и до двух попыток записи. Обе копии создаются сразу; отсутствующая резервная восстанавливается. При повреждении выбирается последняя исправная ревизия; повреждённые байты сохраняются отдельно перед последующей записью, неизвестная версия блокирует загрузку/перезапись. Старый однофайловый UE5.5 schema-1 переносится без изменения оригинала: ограниченный разбор заголовка и сравнение тела после round-trip учитывают разные таблицы custom versions Editor/Game. В тестах закреплён настоящий снимок M1.01 с описанием происхождения.
- **Проверено:** финальные Editor и Game Win64 Development собраны, exit 0 (`Saved/M103/editor-build-final.log`, `game-build-final.log`). Независимый Automation-прогон: 14 результатов, 13 Success + 1 SuccessWithWarnings, 0 Failed; 10 предметных M1.03 и 3 регрессии M1.02, а ProcessRestart в общем прогоне явно пропускает отдельный процессный сценарий. Проверены идемпотентность/вложенные команды, отказ записи и retry, повреждение/усечение одной и обеих копий, сохранность повреждённого оригинала, восстановление отсутствующей копии, перенос старого снимка и отказ неизвестной версии. Отдельные `-game` старты normal/recovered: native GI/Save/Clock готовы, BeginPlay/controller/camera работают, spectator отсутствует; SHA-256 повреждённого и исправного файлов не изменился при загрузке. Артефакты: `Saved/M103/automation-final/`, `process-write/`, `process-read1/`, `process-read2/`, `runtime-user/`, `independent-test-summary.json`.
