**Статус:** решения P18.01–P18.08 согласованы по направлениям. **Q03:** исходные численные определения в неизменяемом C++-каталоге; **Q10:** гибрид C++ + Blueprint там, где это действительно облегчает визуальную разработку; UE5.5 MCP проверить на реальном проекте. **Q13/Q17:** целевая архитектура — авторитетный онлайн-профиль с собственным сервером **и отдельный полностью локальный офлайн/разработческий профиль**, без доверенного импорта офлайн-достижений; серверную реализацию выполнять только **после работающего игрового цикла**. **Q21–Q28:** экономная тестовая инфраструктура, только локальная машина, отдельные тестировщик и ревьюер, проверка сборки + запуска до commit/push, Steam интегрируется через отдельный адаптер, аудит существующего проекта обязателен. **P18.09 — фактический аудит исходного UE5-репозитория не выполнен**, так как репозиторий не представлен; Документальные правила P18 собраны; фактический аудит **существующего UE-проекта** — отдельная задача `AUDIT-00` после допуска, а не условие законченности текста PRD. **P19.01–P19.08 документально подготовлены для авторского утверждения**, реализация требует отдельного согласия автора на P19.09.

## P18.01–P18.03 — Архитектура игрового цикла

**Утверждено автором:**

- **P18-Q01:** город, тестовая карта и боевые карты — отдельные `.umap` с переходами загрузкой; постоянный профиль вне жизненного цикла отдельной карты.
- **P18-Q02:** при переходе в бой городские Actor-объекты не продолжают работать в памяти. Накопления/работы рассчитываются по пройденному времени и состояниям, с лимитами здания. Ускорение боя ×2/×3 не ускоряет город.
- **P18-Q04:** общее поведение юнитов и небольшие расширяемые C++-обработчики уникальных механик. Абстракция/интерфейс допустимы там, где различается поведение, но не обязателен отдельный Actor-класс под каждое численное значение.
- **P18-Q05:** **никакого runtime-редактора баланса, Hot Reload-функционала для игры и dev-панели**; после изменения C++ допустимы перекомпиляция и повторная загрузка миссии. Выделенный профиль автора используется для игрового тестирования; не создавать dev-console/панель, пока это отдельно не запрошено.
- **P18-Q06:** небольшая собственная система способностей и эффектов; GAS по умолчанию **не включать**; общая обработка активаций, откатов, нанесения урона и статусов; новые уникальные механики — узкие C++-расширения.
- **P18-Q07:** броня — обычное **плоское вычитание**, отдельно для физического и магического урона, никакой формулы множителей.
- **P18-Q08:** отдельно жизненный цикл, действия и наложенные эффекты; несколько эффектов могут сосуществовать.
- **P18-Q09:** типизированные локальные события/delegates, при необходимости узкие уведомления между системами, без обязательного глобального Event Bus; ключевые экономические изменения исполняются одним ответственным владельцем.
- **P18-Q11:** для тестирования отдельный профиль разработчика, без специализированного отладочного меню/песочницы.
- **P18-Q12:** `UE_LOG`/категории, Unreal Insights, предметные тесты инвариантов и отказоустойчивость — обязательны; недопустимы известные UB, утечки, use-after-free, висячие делегаты, повторы наград и повреждение сейвов. **Оркестратор ОБЯЗАТЕЛЬНО назначает отдельного тестирующего субагента и независимого ревьюера. Перед каждым commit и push исполнитель подтверждает успешную сборку, выполнение содержательных unit/integration/сценарных тестов и закрытие замечаний ревью; ложно-положительные/декоративные тесты не засчитываются.** Если в конкретной среде субагенты недоступны, зафиксировать блокер и получить согласование способа независимой проверки, не имитировать отчёт о тестировании. Абсолютную математическую гарантию отсутствия любых багов не обещать.

**Направление выбрано, точная реализация ещё не утверждена:**

- **P18-Q03 — предпочтение автора:** исходные численные характеристики юнитов держать в **именованных неизменяемых C++-определениях**, не в CSV и не в обязательных `UDataTable`. Автор предложил отдельные `const` поля наследников; рекомендуемая для рассмотрения альтернатива — **один универсальный native Actor/системная основа + типизированный компилируемый каталог неизменяемых структур**, чтобы не плодить классы ради цифр. Для чистых POD-чисел допускается `constexpr`; ссылки на ассеты вынести в поддерживаемый UE-тип/реестр. Не делать файловый I/O при атаках; загрузка определения однажды, использование кэшированного состояния. Это решение *не* превращает авторские маршруты/составы волн в C++-хардкод.
- **P18-Q10 — ПРИНЯТО:** использовать гибрид **C++ + Blueprint** там, где Blueprint даёт реальный выигрыш в разработке: Widget Blueprints (UMG), Animation Blueprints, при необходимости визуальные оболочки ассетов/эффектов. Боевая симуляция, экономика, владение состоянием, сохранения, проверки безопасности и тяжёлые циклы — C++. **Не** создавать Blueprint-графы вычислений ради графов; проверять работоспособность и стоимость каждого визуального решения. При аудите **точно установить UE5.5 MCP** и реальные операции создания/изменения/компиляции ассетов. Неподдерживаемая операция — честно сообщить автору, предложить проверяемую альтернативу, не заявлять о невозможностях/успехе без теста.

**PROD-GATE-001 и тестовая первая карта:** автор просит использовать первую карту кампании для экспериментов. До принятия полигона допустима только **тестовая/черновая версия геометрии первой миссии, выполняющая роль полигона** без статуса утверждённой финальной сюжетной карты. После `POLYGON_ACCEPTED` допускается превратить её в окончательную миссию. Если автор решит иначе — явно уточнить изменение жёсткого гейта, не считать его отменённым молча. Специальный дорогой редактор разработчика не создавать.
