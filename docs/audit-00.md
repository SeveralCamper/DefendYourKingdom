# AUDIT-00 — состояние проекта и соответствие новой спецификации

Дата: **14.11.2026**. Проверенная база: `4153877`, ветка `main`; до аудита рабочее дерево чистое. Допуск: прямой запрос автора на аудит. Это отчёт о фактах и рекомендации, **не разрешение начинать M1/M2**.

## Вывод

**Кардинальная переделка проекта не нужна. Существующий каркас совместим с новой моделью; нужны адресный рефакторинг и реализация отсутствующих систем.**

Уже выбраны правильные основы: UE5.5, один runtime-модуль, логические `Core/Meta/Saving`, нативные интерфейсы, локальные delegates, профиль вне жизненного цикла карты. Нет большой старой боевой реализации с несовместимыми правилами, которую пришлось бы выбрасывать. Нет оснований вводить дополнительные модули, GAS, глобальный Event Bus или переписывать проект на другую архитектуру.

При этом текущий проект — **ранний технический каркас**, а не готовый M1. Новая спецификация значительно шире реализованного. Особенно важно не принять имеющиеся поля SaveGame за работающие экономику, таймеры, миссии и восстановление прогресса.

Существенно доработать придётся **профиль и сохранения**: текущий прямой доступ к изменяемому SaveGame нельзя распространять на будущие UI, экономику и бой. Сейчас потребителей мало, поэтому эту границу можно исправить без массовой переделки.

## Подтверждённые проблемы и необходимые адаптации

### 1. Профиль: единый владелец команд до появления экономики

[`DYKSaveSubsystem.h:31`](../DefendYourKingdom/Source/DefendYourKingdom/Saving/DYKSaveSubsystem.h) возвращает изменяемый SaveGame. В нём публичны все данные. Нет доменных команд, неизменяемого снимка для UI и общей границы атомарного применения операций.

Рекомендация для `M1.03`: узкий локальный сервис профиля, который проверяет и применяет команды и отдаёт состояние для чтения; сериализация остаётся в Saving. Существующий subsystem можно развить, отдельная иерархия адаптеров/HTTP сейчас не нужна. Покупка, награда, отмена и расход контракта должны иметь одного владельца, контролируемый результат сохранения и защиту от повторного применения.

### 2. Сохранение: текущая реализация недостаточна для Q31

[`DYKSaveSubsystem.cpp:10`](../DefendYourKingdom/Source/DefendYourKingdom/Saving/DYKSaveSubsystem.cpp) использует один `DYK_LocalProfile`. Нет двух чередующихся копий, ревизии, проверки целостности и выбора последней валидной записи. Неизвестная версия отклоняется, но миграций нет. Отдельного пространства профиля автора тоже нет.

Полезную защиту сохранить: повреждённый/неподдерживаемый файл не заменяется новым. Нынешняя запись синхронная, поэтому существующая гонка async-записей **не заявляется**. При последующем переходе на async понадобится сериализованный порядок ревизий.

Схему [`DYKProfileSaveGame.h`](../DefendYourKingdom/Source/DefendYourKingdom/Saving/DYKProfileSaveGame.h) расширять с миграцией существующего v1: экземпляры зданий и накопители, очереди/строители/исследования, герои/контракты, прогресс по режимам/звёздам/выданным наградам, бестиарий. Один BuildingId типа недостаточен для идентичности нескольких одинаковых зданий.

`CurrentMission` с wave/deployment не означает разрешение продолжать прерванную кампанийную попытку. Постоянные траты/открытия сохраняются отдельно; checkpoint межволновой подготовки endless имеет собственный контракт.

### 3. Время: стартовый офлайн-интервал не заменяет экономические часы

[`DYKOfflineClockSubsystem.cpp:23`](../DefendYourKingdom/Source/DefendYourKingdom/Saving/DYKOfflineClockSubsystem.cpp) рассчитывает интервал один раз при создании GameInstance. Нет монотонного времени сессии и повторного расчёта при возвращении из боя; будущая дата может остановить начисления надолго. Обнуление отрицательной разницы полезно, но недостаточно для полного контракта.

В `CommitOfflineCalculation` при ошибке записи откатывается только timestamp. Если вызывающая экономика сначала изменит ресурсы и затем повторит начисление по оставшемуся pending-интервалу, возникнет риск дубля. Сейчас производства и такого вызывающего кода нет: это **дефект предлагаемой границы интеграции**, не воспроизведённое двойное начисление в игре.

Нужны отдельные часы боя и города; ускорение/пауза боя не меняют городское время. Офлайн-прогресс рассчитывается по временным границам завершения работ, а не одним множителем для всего интервала.

### 4. Размещение: локальный дефект и старая терминология

[`DYKPlacementSlotObject.cpp:53`](../DefendYourKingdom/Source/DefendYourKingdom/Core/Placement/DYKPlacementSlotObject.cpp): `Initialize` безусловно меняет Descriptor занятого слота. Статическая цепочка `occupy(A) → Initialize(B) → release` передаёт юниту B, а placeholder очищает размещение только при совпадении сохранённого A. Получается рассогласованное состояние. Исправить запретом переинициализации занятого слота либо корректным освобождением со старым дескриптором.

`SizeInCells` в дескрипторе не соответствует смыслу боевой площадки: её размер — условная метка, общей боевой сетки нет. Сейчас grid-алгоритма здесь нет, поэтому достаточно адаптации контракта. Существующих ранговых/геройских/лучных подтипов слотов не найдено.

В `M1.08` нужны карта-авторские разрешения площадки, фаза, доступность типа, цена и атомарное размещение. Общий обычный слот — для войск, героев и боевых наёмников; совместимость не должна превращаться в индивидуальные ранги слотов у юнитов.

### 5. UI и старт карты

Native delegates выбора пригодны для C++ UI-слоя, но прямо из WBP текущие методы/события не связываются: нет соответствующей reflected-экспозиции. В `M1.10` нужен небольшой presenter/bridge; игровые правила остаются native.

`DYKCityGameMode` сейчас только логирует ошибку профиля. До экономических команд потребуется безопасное состояние ошибки с сообщением пользователю. Настройку параметров камеры через производный BP/CDO следует проверить отдельно: значения переносятся в компоненты в native constructor.

## Архитектурный подход к дальнейшей реализации

Рекомендуется сохранить один модуль и развивать разделение ответственности внутри него:

| Ответственность | Рекомендуемая граница |
|---|---|
| Постоянное состояние | Сервис профиля с командами и снимком; GameInstance-жизненный цикл |
| Диск | Версии/миграции/две копии/ошибки записи в Saving, без доступа UI к `.sav` |
| Город | Компактная модель зданий, очередей и времени вне Actor; Actor/WBP отображают её |
| Попытка боя | Владелец состояния на время мира/миссии; GameMode запускает карту, не содержит все правила |
| Общий бой | Переиспользуемые HP, атака, FIFO-цели, эффекты; узкие расширения уникального поведения |
| Определения | Именованные неизменяемые C++-записи чисел; отдельно изменяемое состояние экземпляра |
| Визуал и сценарий | Мягкие ссылки на ассеты; отдельные карты/маршруты/волны/условия, без хардкода сценария в классе врага |
| События | Узкие типизированные delegates, явные подписки/отписки и порядок; глобальная шина не обязательна |

Точные имена новых классов и выбор ActorComponent/UObject/структур остаются предметом конкретной задачи. Разделять симуляцию и визуал необходимо уже сейчас; строить сервер, запись реплея или самостоятельный универсальный фреймворк не требуется.

## Уточнения утверждённого плана

Порядок **AUDIT → M1-SLICE → M2-FULL → личный POLYGON_ACCEPTED → финальные карты** корректен. Существующий код не позволяет автоматически закрыть какую-либо M1-задачу целиком: у новых критериев Done больший объём.

Перед исполнением стоит внести следующие технические уточнения, сохраняя ID и игровые требования:

1. **`M1.01` — адаптация существующего проекта**, а не повторное создание модуля, подсистем и стартовой карты. Также подтвердить удобный рабочий канал автоматизации UE5.5.
2. **`M1.02` — развить имеющиеся ID.** Каталог DataAsset сейчас не содержит баланса, поэтому конфликта с неизменяемыми C++-характеристиками нет. Не создавать Actor-подкласс ради набора чисел; категории ID расширять без переиспользования уже назначенных значений.
3. **`M1.03` — сразу заложить транзакционный профиль.** `M1.09` уже требует однократной награды, `M2.09` — долговременного расхода контракта. Нельзя отложить всю корректность записи до `M2.19`; там завершать надёжность, миграции и полный набор негативных тестов. Две копии обязательны к M2, ранняя реализация допустима в общей задаче профиля.
4. **`M2.03` — черновик только размещения.** Cancel не должен откатывать живое производство, таймеры и исследования. После `M2.05–07` обязательна повторная интеграционная проверка редактора.
5. **`M2.05/.06/.07` — общий контракт времени/очередей проектировать совместно.** Реализация остаётся по зависимостям; завершение апгрейда посреди отсутствия меняет последующее производство, а не прошлую часть интервала.
6. **`M2.08/.10/.11/.12` — устранить инверсию зависимостей.** Герой и ростер уже требуют умений/аур, но общая система эффектов записана позже и зависит от ростера. Выделить ранний минимальный контракт эффектов, затем наполнять типы, а `M2.12` завершать общие механики и интеграционные проверки. Иначе ранние Done будут преждевременными.
7. **`M1.04/.10` — новая черновая боевая карта и реальный визуальный набор/UI**, а не считать нынешние кубы готовой DEV-MVP-презентацией. Финальные карты, аудио, сервер и реальные платежи остаются вне этих работ.

Это рекомендации аудита. **Нормативный backlog и игровые правила этим отчётом не изменены.**
