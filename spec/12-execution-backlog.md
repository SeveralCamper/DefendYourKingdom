# 12 — P19: детерминированный исполнительный backlog Codex

**Статус:** `PRD-DOCUMENT-READY / AWAITING-EXPLICIT-CODE-START`; этот готовый исполнительный план **не означает команду начать работу**. Фактический `.uproject` ещё предстоит проверить в `AUDIT-00` после допуска. Детальные API, имена существующих классов и реальные зависимости **уточняются после `AUDIT-00`**, не изобретаются в PRD.

## Неподвижные исходные условия

1. **Первое действие оркестратора после разрешения автора — `AUDIT-00`.** ПОЛНОСТЬЮ прочитать `README.md`, `AGENTS.md` и **каждый** файл `spec/`, проверить соответствие документации реальному UE5.5-проекту: `.uproject`, `Source/`, `Config/`, `Content/`, `.umap`, Blueprint, зависимости, плагины, UE5.5 MCP и локальный билд/запуск. Сделать инвентаризацию существующих решений, фактов и несовместимостей. **До аудита нет новых кодовых задач.** Если найдено противоречие с PRD — STOP и решение автора; исправление PRD/плана перед кодом.
2. Для всех следующих задач использовать **одно runtime-модульное решение ADR-0001**, игровые расчёты C++, ограниченные полезные Blueprint/UMG/Animation Blueprint; числа авторских паспортов `10`/`11` не менять. Отсутствующие данные — маркированные `DEV_PLACEHOLDER`, не новые утверждённые правила. Имена/локации игровых UI — по P16.
3. Первая реализация — **только локальная**, отдельный профиль разработчика. Ни серверного API, ни онлайновых профилей, ни античита, ни проверки реплеев, ни публичных рейтингов. Сетевые полномочия запроектированы в P18 и реализуются только после проверенного локального игрового цикла.
4. Для первой сборки нужны **узнаваемые бесплатные лицензированные временные 3D/2D-ассеты**, включая существ, здания, окружение, **все меню и HUD** (иконки, кнопки, панели, портреты, шрифты). Проверять лицензии и размер пакета. **Звук, SFX и музыка НЕ ВХОДЯТ в M1/M2**. Закрытый DEV-MVP, не публичное демо.
5. **`PROD-GATE-001`:** до `POLYGON_ACCEPTED` никакие финальные кампанийные или endless-карты не создавать. Допускается **черновая геометрия предполагаемой первой миссии**, которая служит обязательным полноценным полигоном. После личной приёмки автором может быть превращена в первую настоящую карту.
6. **QA-GATE без показухи (Q36):** перед `git commit`/`git push` — **локальная компиляция** UE-проекта, содержательные применимые тесты/негативные случаи, независимые тестировщик и ревьюер, исправления. **Не** выполнять cook/package, запускать сцену, записывать видео или искать «что показать» для каждой задачи. Запуск требуется для изменённого runtime-поведения и на `M1-SLICE`/`M2-FULL`, но не для чисто структурных, документационных или иных задач без самостоятельного визуального сценария. Упакованную сборку для автора готовить только на контрольном срезе, когда это практически нужно или прямо запрошено. Если проверенный код не изменился до push — достаточно подтвердить тот же проверенный коммит; не считать отсутствие повторной компиляции пропуском проверки. Если среда/ревью/необходимые тесты недоступны — `BLOCKED`, не `DONE`; ложные PASS запрещены. CI и dev-меню не создавать.
7. **Детерминированное исполнение и живой PRD:** выполнять задачи в порядке таблиц и указанных зависимостей; параллелить только независимые задачи после согласования планировщиком и при сохранении QA-GATE. Агент получает **актуальные требования** из предметных `spec/` непосредственно при работе над задачей; если автор обновил характеристики/другие данные, применять новую редакцию, исправляя зависимости/тесты по необходимости. **Не замораживать PRD, не создавать формальный цикл согласования каждой правки.** Не расширять scope; отсутствующий баланс — кратчайший рабочий `DEV_PLACEHOLDER`, но реальный конфликт уже утверждённых правил — остановить затронутую задачу и эскалировать. Технические решения/причины документировать в `docs/implementation-log.md`, не менять PRD ради удобства кода.

8. **Отчётность и документация реализации (Q38):** на каждой завершённой задаче кратко сообщить автору **что сделано, какие решения приняты и почему**; добавить такую же краткую фактическую запись в **[`docs/implementation-log.md`](../docs/implementation-log.md)** проекта. Не менять ради отчётности нормативный PRD `spec/`; документация описывает реализованное, PRD задаёт требуемое. Большой отчёт — только для `AUDIT-00`, `M1-SLICE`, `M2-FULL` и блокирующих отклонений. **Параллельность (Q37):** субагенты могут выполнять параллельно только задачи без конфликтующих зависимостей/файлов/ассетов; интеграция и QA-GATE контролируются оркестратором.
**Утверждённые механики Q40–Q42 (обязательные для M2):**

- `TIME-MODE` / Q40: строить, улучшать, исследовать **по таймерам** с очередями и отдельной исследовательской ячейкой; продолжение в офлайне; длительности предметного контента допускаются `DEV_PLACEHOLDER`, но система таймеров — не заглушка.
- `P11-LIFE` / Q41: только в `CHALLENGE_5` **у всех защищаемых зданий и объектов HP=MaxHP=1**; войска/воскрешение/повторные попытки прежние; использовать тот же контракт поражения.
- `P08-C1` / Q42: активные длительные боевые эффекты **полностью завершаются на границе каждой волны**; не замедляются, не переносятся.

## Работа после полного полигона и контроль дальнейшего этапа

- **`ACCEPT-01`:** автор вручную испытывает `M2-FULL` и явно выдаёт `POLYGON_ACCEPTED` либо перечень замечаний. Отдельная итерация исправлений → повторное тестирование при отказе.
- **`CAMPAIGN-01` (только после `POLYGON_ACCEPTED`):** завершение **первой настоящей миссии кампании** на принятом функциональном фундаменте; затем отдельно согласуем конкретные авторские карты/волны, не выдумываем массово содержание девяти миссий.
- **`ONLINE-01+` (отдельная поздняя дорожная карта):** после принятого локального цикла серверное хранение онлайн-профиля, авторитетное время/ресурсы, подтверждение команд, реплей-проверка результатов, Steam/рейтинги. Эти пункты **не включены в первую локальную реализацию**.
- **`AUDIO-LATER`:** поиск/производство, импорт и программирование SFX и музыки только по отдельному разрешению автора; старые P17-требования сохранены, но не препятствуют `M1`/`M2`.

## Обязательный минимальный контракт каждой исполняемой задачи

Каждая задача текущего плана при исполнении имеет: **стабильный ID**, ссылки на конкретные нормы PRD, входные зависимости, определённый функциональный результат, применимые предметные и негативные проверки, критерий Done, владельцев (исполнитель/тестировщик/ревьюер), маркер `DEV_PLACEHOLDER` при необходимости и локальный QA-гейт до commit/push. **«Способ показать результат» нужен только когда у задачи есть реальный визуально проверяемый результат.** Каждая закрытая задача получает короткую запись в `docs/implementation-log.md` (что / какие решения / почему / проверка). Не выдумывать существующие имена классов без аудита. Никаких фиктивных PASS.

**До реализации:** явный допуск автора; затем аудит сборки/MCP (`AUDIT-00`) в среде Codex и устранение реально найденных блокеров. **Q36–Q38 согласованы:** нет упаковки или демонстрации каждой задачи; параллельны только независимые задачи; краткая отчётность и отдельный `docs/implementation-log.md`. Неизвестные числа не блокируют локальный MVP: `DEV_PLACEHOLDER`.

## P19.07 — сроки и объём подготовки Steam (Q43-Б, APPROVED)

- **Только после играбельного `M2-FULL`** начинать страницу магазина Steam: реальные кадры игры, корректное описание доступных функций, выбранные языки, необходимые изображения и перечень требований площадки. ## P19.08 — актуальный PRD без заморозки (Q44, правило автора)

- `spec/` — **живой источник требований**. На `AUDIT-00` прочитать весь PRD, в ходе работы — соответствующие **актуальные** файлы. Не продолжать реализовывать правило по устаревшей выписке после изменения автора.
- Автор может изменять характеристики, баланс, текст и правила. При изменении очередной задачи использовать новые данные; если существующий код затронут, адаптировать его и провести предметные проверки. Git хранит историю правок, а `docs/implementation-log.md` — только принятые технические решения и причины.
- **Никаких baseline-lock, change-request или дополнительной согласовательной процедуры для каждой правки.** Если изменение приводит к реальному противоречию с другим явным авторским правилом или неподдающемуся автоматической корректировке архитектурному блокеру — сообщить конкретную проблему, не задавать новые вопросы ради формальности.
