# 13 — P19.01–P19.05: матрица требований → задачи → предметные проверки

**Документальная трассировка готова:** все 36 задач имеют источники и проверки. Реальный UE5-проект не входит в этот архив; аудит/запуск проводятся только после команды автора. Источник задач — [`12-execution-backlog.md`](12-execution-backlog.md); источник проверки результата — [`09-qa.md`](09-qa.md).

## Метод и граница трассировки

1. Строка ниже связывает **утверждённую норму или явное проектное ограничение** с будущей задачей и существующим QA-сценарием. Это **не** означает, что реализация существует. `A00` подтверждается отчётом аудита, а не выдуманными игровыми тестами.
2. Записи `Pxx` и `CITYxx` указывают на именованные разделы соответствующего нормативного файла. Паспорта `10` и `11` приоритетны для чисел; любые пропущенные числа маркируются `DEV_PLACEHOLDER` **в реализации**, не записываются в авторские документы как утверждённые.
3. Метки `M1`/`M2` — **обязательный функциональный результат своей стадии**, `PRD-GATE` — работа аудита. Избранные QA-тесты являются **минимальными примерами ключевых проверок**, но не отменяют другие применимые сценарии из `09`.
4. Каждая задача обязана иметь в момент исполнения реальные входные данные/команды/ожидаемый результат; тесты отмечают `PASS` только после выполнения. Где стоит `CONDITIONAL`, в M2 требуется короткая временная политика без подмены авторской механики либо решение автора, если без него невозможно реализовать поведение.
