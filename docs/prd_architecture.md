🏛️ ЧАСТЬ 1: Модульная структура приложения

Исходный вариант архитектуры предлагает три независимых C++ модуля для оптимизации времени компиляции и разделения логики. Это предложение требует проверки: текущий проект содержит один модуль, а окончательные границы и зависимости будут выбраны в отдельном архитектурном решении с учётом [видения MVP](mvp_vision.md) и [плана задач](mvp_task_plan.md).

1. DYKSaving

• Предлагаемая зона ответственности: базовые C++ структуры данных (FPlayerInventory, FBuildingState) и сериализация локальных сохранений. Интеграция со Steam (облачные сохранения, достижения, статистика) отложена за пределы MVP.
• Связи: Является базовым модулем. Не имеет внешних зависимостей внутри проекта.

2. DYKCore

• Зона ответственности: Логика боевой сессии Tower Defense (башни, спавнеры, навигация врагов, обсчет урона).
• Связи: Зависит от DYKSaving. Принимает на вход массив структур данных инвентаря игрока при инициализации уровня. Выгружается из памяти вне боевой сессии.

3. DYKMeta

• Зона ответственности: Логика Цитадели (строительство, кузница, очереди крафта ловушек между матчами).
• Связи: Зависит от DYKSaving и DYKCore.
• Фоновые таймеры: Расчет времени производства реализован через подсистему UGameInstanceSubsystem на основе сверки Unix Timestamp (FDateTime::UtcNow().ToUnixTimestamp()). Физические таймеры в рантайме во время боя не используются.

1. Камера и Ввод игрока

• Класс: Кастомный APawn + USpringArmComponent + UCameraComponent + Enhanced Input System.
• Реализация: Перемещение в плоскости XY через AddActorWorldOffset. Ограничение игрового поля через FMath::Clamp для координат актора. Компонент USpringArmComponent зафиксирован под углом Pitch -45° без физического тика.

2. Оборонительные башни

• Класс: AActor + Модульные UActorComponent.
• Реализация: Статичные акторы с отключенным основным тиком (PrimaryActorTick.bCanEverTick = false;). Вся боевая логика (поиск целей, стрельба) инкапсулирована в компонентах.

3. Враги и Стражи на дорогах

• Класс: ACharacter + AAIController.
• Реализация: Максимальный лимит одновременных сущностей на сцене — 100 единиц. Движение и обход препятствий реализуются через нативный UCharacterMovementComponent с включенной подсистемой обхода RVOAvoidance по сетке NavMesh.

1. Поиск целей оборонительными башнями

• Алгоритм: Нативная функция UKismetSystemLibrary::SphereOverlapActors по таймеру.
• Спецификация: Запуск опроса физического подпространства (Chaos Physics) по каналу коллизий противников с интервалом в 0.2с через FTimerManager. Логика фильтрации выборки: приоритет по минимальному остаточному здоровью или по максимальной дистанции вдоль пути движения.

2. Сетка слотов для Стражей

• Структура: TMap<FIntPoint, ADefenderSlotActor*>
• Спецификация: Двумерная координатная сетка уровня для мгновенного доступа \(O(1)\) к интерактивным гнездам призыва при валидации кликов мыши через GetHitResultUnderCursorByChannel.

3. Очередь спавна врагов

• Структура: TQueue<FEnemySpawnPacket, EQueueMode::Mpsc>
• Спецификация: Потокобезопасная FIFO-очередь для асинхронного наполнения менеджером волн и последовательного извлечения пакетов спавнера на сцене.

## ЧАСТЬ 4: План реализации MVP

Подробная декомпозиция исходного бэклога с учётом подтверждённого видения игры вынесена в отдельный документ: [План задач MVP](mvp_task_plan.md). Он заменяет прежние четыре укрупнённых этапа и указывает порядок, границы и критерии готовности небольших задач.

Технические решения из частей 1–3 этого документа остаются исходными предложениями до проверки и принятия в архитектурном решении MVP-05.
