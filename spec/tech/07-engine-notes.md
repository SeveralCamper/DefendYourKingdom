## Архитектурные основы и необходимость аудита (P18)


**Статус:** технические требования; фактическое состояние существующего UE-проекта устанавливается только аудитом `AUDIT-00`.

## 1. Что уже принято в прежней документации

Из `docs/adr/0001-runtime-module-boundaries.md` (принято автором 2026-10-25):

- UE 5.5; один runtime-модуль `DefendYourKingdom`.
- Логические каталоги исходников `Core`, `Meta`, `Saving`, без создания `DYKCore`, `DYKMeta`, `DYKSaving` в MVP.
- Геймплейная логика реализуется на нативном C++; Blueprint допускается для UI, анимаций и визуального представления там, где это действительно проще и проверено в UE5.5. Числовые характеристики типов предпочтительно задаются C++-описаниями. Data Assets / Data Tables допустимы для конфигурации и контента.
- Узкие контракты между системами; `UInterface` для действительно разных реализаций; корректные ссылочные отношения `UObject`.
- Локальный профиль на `USaveGame`; Unix timestamps для офлайн-времени; об ошибке повреждённого/несовместимого файла сообщать, не затирая его автоматически.

**Нормативная архитектура:** один runtime-модуль `DefendYourKingdom`, логические каталоги `Core/`, `Meta/`, `Saving/`; дополнительные runtime-модули без причины не создавать.

## 3. Что проверять перед задачами на код

1. Совпадают ли существующие `UDYKProfileSaveGame`, контракты слотов и модель миссии с новыми правилами, включая **внутримиссионный учёт уже активированных, но снятых со слота наёмников**.
2. Как однократно и долговременно подтвердить расход контракта при первом старте волны с новым отрядом; при рестарте контракты не возвращаются, до первой волны — не списываются.
3. Как определяются и сохраняются текущий уровень волны, наёмник «ещё не использован»/«уже использован», смерть и откат.
4. Как проектируется отмена/пауза/выход из миссии без получения бесплатных контрактов или нечестной потери.
5. Нужна ли в будущем защита покупной валюты и контрактов от изменения локального времени/сохранений (Steam-публикация сама по себе не делает локальные данные достоверными).

## 4. Ограничения этой справки

**Не вводить автоматически:** дополнительный модуль, объектную фабрику как обязательную, новый enum, сетевой backend, инвентарь экземпляров обычных войск, отдельный UI резерва, ограничение числа отрядов казармами, фиксированные числа баланса или новую схему сохранения.

Перед техническим решением — сначала завершить геймдизайн соответствующей системы и оценить реальную реализацию проекта.

## P05 — требования к будущему проектированию C++ (не принятое устройство классов)

- Единый событийно-обновляемый **упорядоченный пул целей** для всех союзных/вражеских атакующих по [`E09.03`](../07-content-and-magic.md#e0903--единый-механизм-упорядоченного-пула-целей-для-всех-юнитов): вход в радиус, стабильный порядок, удержание цели, удаление мёртвых/недоступных ссылок; без физического LOS и без постоянного пересчёта «ближайшего».
- Синхронизация расчётного **момента попадания** с анимацией обязательна; не создавать физический projectile Actor для визуальных выстрелов. Отдельно проверять поведение смерти цели до воздействия, отмены при оглушении, «выпущенного» визуального эффекта и паузы/ускорений ×2/×3.
- В UE существуют **Animation Notifies**, которые позволяют синхронизировать события с анимацией, но их применение (включая нативные обработчики и альтернативные data-driven тайминги) **не выбрано архитектурным решением**. Проверить поддержку в закреплённой UE 5.5, учитывая C++-only ADR. Источник для будущей проверки: https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-notifies-in-unreal-engine .
- Не вводить для всех юнитов стохастический блок/крит по умолчанию; только специально сконфигурированные типы.
- Для AoE требуется единоразовое воздействие на каждую допустимую сущность внутри одной активации (или управляемые периодические тики в рамках длительного эффекта) без лимита пересекающихся моделей.
- Q01 о композиции возможностей относится к **P18**, не трактовать отсутствие ответа как разрешение на конкретную архитектуру GAS/ActorComponents.
